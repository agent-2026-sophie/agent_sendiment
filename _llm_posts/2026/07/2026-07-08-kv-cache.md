# KV Cache 缓存命中

## 1. KV Cache 基础概念

### 1.1 什么是 KV Cache

在 LLM（大语言模型）的自回归推理过程中，每生成一个新 token，都需要对之前所有 token 的 Key 和 Value 矩阵进行注意力计算。如果不做缓存，每一步都要重新计算所有历史 token 的 K/V，计算复杂度为 O(n²)。

**KV Cache** 的核心思路是：将已计算过的 Key 和 Value 张量缓存在 GPU 显存中，后续生成新 token 时只需计算当前 token 的 K/V 并追加到缓存中，避免重复计算，将每步复杂度降为 O(n)。

### 1.2 缓存命中（Cache Hit）的含义

**缓存命中**指的是：在处理当前请求时，所需的 KV Cache 数据已经存在于缓存中，可以直接复用，无需重新计算。

这与具体的缓存策略相关，常见场景包括：

#### Prefix Cache（前缀缓存命中）

这是最核心的缓存命中场景。多个请求共享相同的前缀（如 system prompt、few-shot examples、共享上下文），那么这部分前缀对应的 KV Cache 只需计算一次，后续请求命中后直接复用。

```
请求A: [system_prompt] [few_shot] [用户问题A]
请求B: [system_prompt] [few_shot] [用户问题B]
              ↑ 共享前缀，KV Cache 命中
```

#### Session/多轮对话缓存命中

在多轮对话中，前几轮的 KV Cache 可以保留，新一轮对话只需计算新增的 token，历史部分命中缓存。

## 2. Prefill 与 Decode 阶段

LLM 的推理过程分为两个阶段：**Prefill（预填充）** 和 **Decode（解码）**。理解这两个阶段对于理解缓存命中至关重要。

### 2.1 Prefill 阶段

**Prefill（预填充）** 是推理的第一个阶段，负责处理用户输入的 prompt（即输入序列），为所有输入 token 计算并填充 KV Cache。

- **输入方式**：一次性接收整个 prompt 序列，并行计算
- **计算特点**：计算密集型（compute-bound），GPU 算力利用率高
- **输出**：第一个生成 token（即首 token），以及填充好的 KV Cache
- **耗时特征**：与 prompt 长度成正比，长 prompt 的 Prefill 耗时显著

### 2.2 Decode 阶段

**Decode（解码）** 是 Prefill 之后的自回归生成阶段，逐个生成后续 token。

- **输入方式**：每次只输入上一个生成的 token（单 token 输入）
- **计算特点**：访存密集型（memory-bound），GPU 算力利用率低
- **KV Cache 作用**：每步将新 token 的 K/V 追加到缓存中，下一步直接从缓存读取历史 K/V
- **耗时特征**：与生成长度成正比，单步计算量小但总步数多

### 2.3 两阶段对比

| 维度 | Prefill | Decode |
|---|---|---|
| **处理内容** | 用户输入的 prompt | 逐个生成的 token |
| **输入 token 数** | 全部 prompt token（并行） | 每次仅 1 个 token |
| **计算类型** | 计算密集型（compute-bound） | 访存密集型（memory-bound） |
| **GPU 利用率** | 高 | 低 |
| **KV Cache 行为** | 从零计算并填充 KV Cache | 增量计算并追加到 KV Cache |
| **性能指标** | TTFT（首 token 延迟） | TPOT（每 token 延迟）、吞吐 |

## 3. 两阶段的缓存命中

### 3.1 Prefill 阶段的缓存命中

在 Prefill 阶段，缓存命中的核心场景是 **Prefix Cache（前缀缓存复用）**。

**工作原理：**

1. 新请求到达时，将输入 prompt 与缓存中已有请求的前缀进行匹配
2. 匹配到的前缀部分对应的 KV Cache 直接从缓存中加载，跳过这部分的前向计算
3. 仅对 prompt 中**不匹配的后缀部分**进行 Prefill 计算

**示例：**

```
已有缓存（来自请求A）:
  [system_prompt] [few_shot] [问题A] → KV Cache 完整缓存

新请求B:
  [system_prompt] [few_shot] [问题B]
  └── 命中 ──┘    └── 未命中，需计算 ──┘
```

**收益：**

- 显著降低 TTFT（首 token 延迟）
- 减少 Prefill 阶段的 FLOPs 计算量
- 特别适合 system prompt 固定、few-shot 模板统一的场景

### 3.2 Decode 阶段的缓存命中

Decode 阶段的缓存命中主要体现在以下场景：

#### 多轮对话中的历史复用

在多轮对话中，前几轮对话的 KV Cache 已经存在于显存中。新一轮对话的 Decode 阶段可以直接使用已有的历史 KV Cache，无需重新计算。

```
第1轮: [system] [Q1] [A1]          → 全部 KV Cache 存入缓存
第2轮: [system] [Q1] [A1] [Q2] [A2(生成中)]
         └── 全部命中缓存 ──┘  └── 新增，增量计算 ──┘
```

#### 跨请求的 KV Cache 保留

在某些场景下（如对同一 prompt 的多次采样生成），可以保留 Prefill 阶段的 KV Cache，后续请求的 Decode 直接复用。

**注意：** Decode 阶段本身的 KV Cache 是增量构建的，每生成一个新 token 都会将该 token 的 K/V 追加到缓存中。因此 Decode 阶段的"命中"更多是指**历史 KV Cache 的复用**，而非每步内部的命中。

### 3.3 两阶段缓存命中对比

| 维度 | Prefill 阶段缓存命中 | Decode 阶段缓存命中 |
|---|---|---|
| **命中对象** | 输入 prompt 的前缀部分 | 历史对话/历史请求的 KV Cache |
| **命中机制** | Prefix Cache 前缀匹配 | Session Cache / 跨请求缓存保留 |
| **命中收益** | 跳过前缀部分的前向计算，降低 TTFT | 跳过历史 token 的 KV 重新计算 |
| **典型场景** | system prompt 共享、few-shot 模板复用 | 多轮对话续接、同一 prompt 多次采样 |
| **收益大小** | 显著（Prefill 是计算密集型） | 相对有限（Decode 本身访存密集，单步计算量小） |

## 4. 缓存命中率的关键影响因素

| 因素 | 说明 |
|---|---|
| **前缀匹配长度** | 共享前缀越长，命中后节省的计算越多 |
| **缓存淘汰策略** | 显存有限，LRU/LFU 等策略影响哪些缓存被保留 |
| **请求调度** | 将共享前缀的请求调度到同一节点，才能命中同一块缓存 |
| **模型架构** | GQA/MQA 等减少了 KV Cache 大小，间接影响能缓存的序列数量 |

---

## 5. 缓存命中的收益

- **降低首 token 延迟（TTFT）**：Prefill 命中部分无需前向计算，直接加载已有 KV
- **减少计算量（FLOPs）**：命中部分省去 attention 中的 K/V projection 计算
- **提升吞吐**：GPU 算力释放出来可用于处理更多并发请求
- **降低成本**：减少 GPU 计算时间，直接降低推理成本

---

## 6. 常见的实现方案

| 框架 | 实现机制 |
|---|---|
| **vLLM** | PagedAttention + Prefix Caching，自动前缀复用 |
| **SGLang** | RadixAttention 树结构管理共享前缀的 KV Cache |
| **TensorRT-LLM** | KV Cache Reuse，跨请求复用相同前缀 |
| **TGI** | 内置 prefix caching 机制 |

---

## 7. 小结

KV Cache 缓存命中的本质是 **跨请求/跨轮次复用已计算的 Key-Value 张量**，核心价值在于减少重复计算、降低延迟、提升吞吐。

- **Prefill 阶段**的缓存命中主要通过 **Prefix Cache** 实现，跳过共享前缀的前向计算，显著降低 TTFT
- **Decode 阶段**的缓存命中主要通过 **Session Cache / 跨请求缓存保留** 实现，避免历史 token 的 KV 重新计算

在实际部署中，Prefix Cache 是收益最高的场景，尤其适合 system prompt 固定、few-shot 模板统一、多轮对话等业务模式。
