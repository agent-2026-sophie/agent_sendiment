一句话:**它们不在同一个层次上。** HTTP/REST 是"传输层 + 通用 Web 接口风格",MCP 是"专为 AI Agent 调用工具设计的应用层协议",而且 MCP 实际上**还是跑在 HTTP 之上的**。所以严格说不是二选一的对立关系,而是"MCP 用了 HTTP 做底层传输,并在上面加了一套面向大模型的标准约定"。

---

## 核心区别对比

| 维度 | HTTP/REST API | MCP(Model Context Protocol) |
|---|---|---|
| **定位** | 通用的 Web 接口风格,面向"程序员写代码调用" | 面向"大模型/Agent 自主发现并调用工具"的标准协议 |
| **底层传输** | HTTP | 通常也是 HTTP(streamable-http / SSE),或本地 stdio |
| **消息格式** | 自由,通常是各家自定义的 JSON 结构 | 统一用 **JSON-RPC 2.0** |
| **谁来调用** | 人类开发者按文档拼请求 | LLM 根据工具描述**自己决定**调哪个、传什么参数 |
| **能力发现** | 没有标准,靠人读 API 文档 | 内置 `list_tools` 等,Agent 可**运行时自动发现**有哪些工具、参数是什么 |
| **接口粒度** | 一个个 endpoint(如 `GET /stock/AAPL`) | 一个个"工具/资源/提示词"(Tool / Resource / Prompt) |
| **接入成本** | 每对接一个 API 都要单独写适配代码 | 支持 MCP 的 Agent(Claude、Cursor 等)**零改造即插即用** |
| **状态** | REST 强调无状态 | 支持有状态会话、长连接、流式推送 |

---

## 关键差异展开

### 1. 调用主体不同(最本质的区别)
REST 是给"确定性程序"用的——你写死代码 `requests.get(...)`。MCP 是给"不确定的大模型"用的——模型看着工具的自然语言描述,**自主判断**该不该调、调哪个、参数怎么填。所以 MCP 的工具定义里非常强调"给模型看的描述",而不只是给人看的字段类型。

### 2. 标准化程度不同
每个 REST API 的 URL 路径、参数命名、返回结构都不一样,Agent 想用就得为每家单独适配。MCP 把这些统一成一套规范(JSON-RPC + 标准的工具/资源发现机制),因此一个 Agent 客户端可以用同一套逻辑对接成千上万个 MCP server。这也是为什么万得等厂商选择用 MCP 对外开放——任何支持 MCP 的 Agent 都能直接接。

### 3. 能力发现机制
用 REST 你得先读文档才知道有哪些接口;MCP 客户端连上 server 后可以**动态拉取**当前有哪些工具及其参数 schema,模型据此即时理解能力边界。

---

## 类比理解

- **REST** 像"每家餐厅一份格式各异的菜单,你(开发者)得逐一研究怎么点";
- **MCP** 像"统一标准的点餐系统,任何顾客(AI Agent)进任何店都用同一套流程,而且系统会主动告诉你今天有哪些菜可点"。

---

## 结论

- 不是"MCP vs HTTP"的替代关系:**MCP 本身通常就架在 HTTP 上**,只是在传输之上规定了一套面向 AI 的应用层约定。
- 真正对立的是 **"MCP 标准工具协议" vs "自定义 REST API"** 这两种对外暴露风格。
- **如果接口是给 AI Agent 用的 → 选 MCP**(自动发现、免适配、模型友好);**如果是给传统程序/前端用的 → REST 更直接通用**。

> 场景示例:万得 Wind Alice 选 MCP 而不是裸 REST,正是因为目标使用者是 AI Agent,要的就是"任何支持 MCP 的 Agent 零改造即插即用"这个特性。
