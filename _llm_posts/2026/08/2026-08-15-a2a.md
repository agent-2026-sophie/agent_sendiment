## 一、A2A 是什么

**Agent2Agent(A2A)协议**是一个开放标准,用于在**独立、彼此"不透明"的 AI Agent 系统之间**实现通信与互操作。在一个 Agent 可能由不同框架(LangGraph、CrewAI、Google ADK 等)、不同语言、不同厂商构建的生态里,A2A 提供了一套统一的"通用语言"和交互模型([Agent2Agent (A2A) Protocol Specification](https://a2a-protocol.org/latest/specification/))。

它由 Google 于 2025 年 4 月发布,随后捐赠给 **Linux Foundation** 进行中立治理,当前最新正式版本为 **v1.0.0**。发布一年内已有 **150+ 家组织**参与,并进入各大云平台、开始出现企业生产环境落地([A year of open collaboration](https://opensource.googleblog.com/2026/04/a-year-of-open-collaboration-celebrating-the-anniversary-of-a2a.html))。

**一句话定位**:如果说 MCP(Model Context Protocol)解决的是"Agent ↔ 工具/数据"的连接,那么 A2A 解决的是"Agent ↔ Agent"的协作与委派。二者互补而非替代。

### 核心设计原则

A2A 的关键目标是**互操作、协作、发现、灵活、安全、异步优先**,其指导原则如下:

- **Simple(简单)**:复用成熟标准 —— HTTP、JSON-RPC 2.0、Server-Sent Events(SSE)。
- **Enterprise Ready(企业就绪)**:内建认证、授权、安全、隐私、链路追踪与监控,对齐企业实践。
- **Async First(异步优先)**:面向可能非常长的任务与 human-in-the-loop(人在环)场景设计。
- **Modality Agnostic(模态无关)**:支持文本、音视频(通过文件引用)、结构化数据/表单,乃至嵌入式 UI 组件。
- **Opaque Execution(不透明执行)**:Agent 之间**只基于声明的能力和交换的信息协作,无需暴露各自的内部思考、计划或工具实现**——这是 A2A 最重要的安全与解耦原则。

## 二、核心概念与技术架构

### 关键概念

| 概念 | 说明 |
|---|---|
| **A2A Client** | 代表用户或系统发起请求的应用/Agent |
| **A2A Server(Remote Agent)** | 暴露 A2A 兼容端点、处理任务并返回结果的远端 Agent |
| **Agent Card** | 一份 JSON 元数据文档,描述 Agent 的身份、能力、技能(skills)、服务端点和认证要求 —— 是 Agent 的"数字名片",用于被发现 |
| **Message** | 一次对话轮次,带 role(user/agent),包含一个或多个 Part |
| **Task** | A2A 管理的基本工作单元,有唯一 ID,**有状态**并遵循定义好的生命周期 |
| **Part** | Message/Artifact 中最小的内容单元(文本、文件引用、结构化数据) |
| **Artifact** | 任务产出的结果(文档、图片、结构化数据),由 Part 组成 |
| **Streaming** | 通过 SSE 实时增量推送状态变化和产物分片 |
| **Push Notifications** | 服务端主动向客户端 webhook 发 HTTP POST,用于长任务/断线场景 |
| **Context / Extension** | 逻辑分组多个相关任务;扩展核心协议之外的能力 |

### 三层规范架构

A2A v1.0 规范采用**三层分离**设计,保证语义一致、可扩展新绑定:

1. **Layer 1 — 规范数据模型(Canonical Data Model)**:定义所有实现都必须理解的核心数据结构(Task、Message、AgentCard、Part、Artifact、Extension),以 **Protocol Buffer** 表达,协议无关。`spec/a2a.proto` 是**唯一权威规范来源**,其余 SDK/JSON Schema 均由它生成。
2. **Layer 2 — 抽象操作(Abstract Operations)**:定义 Agent 必须支持的基本能力,与具体传输无关 —— Send Message、Send Streaming Message、Get Task、List Tasks、Cancel Task、Get Agent Card。
3. **Layer 3 — 协议绑定(Protocol Bindings)**:把抽象操作映射到具体传输 —— **JSON-RPC 2.0、gRPC、HTTP/REST**,以及自定义绑定。

### 典型工作流

发现(读取对方 Agent Card)→ 建立任务(发起 Message)→ 协作执行(流式更新 / 推送通知,期间可 human-in-the-loop)→ 返回 Artifact。任务在其生命周期中经历 `submitted → working → input-required → completed / failed / canceled` 等状态。

## 三、A2A vs MCP:互补关系

| 维度 | A2A | MCP |
|---|---|---|
| 解决问题 | Agent ↔ Agent 协作与任务委派 | Agent ↔ 工具/数据源连接 |
| 交互对象 | 对等的、自治的远端 Agent | 从属的、被调用的工具/资源 |
| 核心抽象 | Task / Message / Agent Card | Tool / Resource / Prompt |
| 关系 | 一个 Agent 可同时**用 MCP 接工具**,并**用 A2A 与别的 Agent 协作** | 两者常组合使用 |

官方明确定位二者互补:MCP 让单个 Agent 具备能力,A2A 让多个 Agent 组成协作网络。

## 四、如何评估 A2A(重点)

评估 A2A 需要区分**两个层面**:(A)评估某个实现是否**合规/符合协议**;(B)评估基于 A2A 构建的**多 Agent 系统效果好不好**。二者要分开做。

### 层面 A:协议合规性评估 —— 官方 TCK

A2A 项目提供官方 **TCK(Technology Compatibility Kit,技术兼容性套件)**,仓库为 `a2aproject/a2a-tck`,是评估一个 Agent 实现"是否真正符合 A2A 规范"的权威工具。它将测试按**规范约束级别**分类,对应 RFC 2119 的 MUST/SHOULD/MAY:

| 测试类别 | 含义 | 通过要求 |
|---|---|---|
| **Mandatory(强制)** | 对应规范中的 MUST/SHALL 要求 | **必须全部通过**,否则不合规 |
| **Capability(能力)** | 声明支持某能力(如 streaming、push)时,该能力必须正确实现 | 声明了就必须通过 |
| **Quality(质量)** | 生产健壮性(并发、边界、错误恢复) | 建议通过,反映成熟度 |
| **Feature(特性)** | 可选特性的实现完整度 | 可选 |

**评估要点**:
- **合规性验证**:JSON-RPC 2.0 报文格式、方法映射、错误码是否符合规范;Agent Card 字段是否完整、可被发现。
- **任务生命周期正确性**:状态流转(submitted/working/input-required/completed/failed/canceled)是否合法;Cancel、Get、List Task 行为是否正确。
- **能力一致性**:声明的 streaming(SSE)、push notification 等能力是否真实可用 —— "声明即契约"。
- **多绑定一致性**:同一 Agent 在 JSON-RPC / gRPC / REST 下语义是否一致。
- **互操作性测试**:与用不同框架/语言实现的 A2A Agent 实际对接联调,验证跨实现协作。

### 层面 B:基于 A2A 的多 Agent 系统效果评估

协议合规不等于系统好用。对上层多 Agent 应用,需借助通用 **AI Agent 评估方法**,核心是区分**轨迹指标(trajectory)**与**结果指标(outcome)**([How to Build an Agent Evaluation Framework](https://galileo.ai/blog/agent-evaluation-framework-metrics-rubrics-benchmarks))。Agent 的失败方式与普通 LLM 不同:可能选对了工具却传错参数、制定了好计划却没执行、完成了任务却浪费大量冗余步骤 —— 因此必须基于**完整执行轨迹(execution trace)**评估([AI Agent Evaluation Metrics](https://deepeval.com/guides/guides-ai-agent-evaluation-metrics))。

**建议评估维度(针对 A2A 协作场景)**:

1. **任务成功率(Task Success Rate)**:端到端任务是否达成用户目标(结果指标)。
2. **委派/路由准确性**:主 Agent 是否把子任务正确路由给合适的远端 Agent(A2A 特有)。
3. **Agent 发现与选择质量**:基于 Agent Card 的能力匹配是否准确。
4. **协作轨迹质量**:跨 Agent 的消息交换是否高效,有无冗余往返、死循环(轨迹指标)。
5. **上下文/状态一致性**:多任务通过 Context 分组时,状态、Artifact 传递是否无损。
6. **鲁棒性与错误恢复**:远端 Agent 失败、超时、返回 input-required 时的处理。
7. **延迟与成本**:长任务的流式/推送时延,总 token 与调用次数。
8. **安全与合规**(企业关键):
   - Agent Card 认证声明是否被强制执行;
   - "不透明执行"是否守住 —— 是否泄漏了不应暴露的内部状态/工具;
   - 跨 Agent 授权边界、数据出域控制;
   - 恶意/伪造 Agent Card 的防护。

**落地方法**:
- 用 **LLM-as-judge** 对轨迹和结果打分,目标与人工判断的相关性达 Spearman **0.80+**。
- 用**多层 rubrics**(维度 → 子维度 → 具体条目)细化标准。
- 结合领域基准(如 WebArena、GAIA、SWE-bench)选取匹配自身场景的题集。
- 将评估集成进 **CI/CD**(提交触发、定时、事件触发),在上线前拦截回归。
